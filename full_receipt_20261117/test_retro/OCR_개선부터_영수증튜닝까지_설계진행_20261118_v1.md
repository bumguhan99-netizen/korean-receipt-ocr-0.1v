## 1. 이 파일을 읽은 다음 작업자의 실행 지침

목표는 기존 개선안을 구현·검증하고, `dataset/receipt_labeled`의 검증된 스마트폰 영수증으로 인식기를 튜닝한 뒤 export·전체 파이프라인 비교·최종 채택 판단까지 마치는 것이다. 계획 설명이나 학습 시작만으로 완료 처리하지 않는다. 이 파일은 해당 작업을 순서대로 수행하고 중단 후 재개하기 위한 진입점이다.

사용자가 이 파일에 따라 실행하도록 요청하면 S00부터 실제 파일 상태와 완료 증거를 확인하고, 완료된 단계를 재실행하지 않은 채 다음 단계로 진행한다. 설치·환경 구성은 기존 승인 범위에서 필요한 경우 수행하되 정상 환경을 반복 설치하지 않는다. 자동 재부팅·기존 결과 삭제·서비스 자동 배포는 실행 단계에 포함하지 않는다.

원본 코드·데이터·라벨·모델·기존 결과는 보존한다. 새 코드는 버전을 나누고 실행마다 새 폴더를 만든다. 이 문서도 기존 내용을 덮어쓰기보다 새 버전이나 별도 진행 기록으로 이어간다. 한국어로 진행 상황과 한계를 보고한다.

현재 요청으로 작성한 것은 이 **설계·진행 파일**이다. 아래 체크 항목은 실제 성공 증거가 생기기 전에는 완료로 바꾸지 않는다. 신규 test·완전 GT가 부족하면 그에 의존하는 검증만 대기하고, 가능한 개선 구현·학습·dev 평가를 계속한다.

## 3. 최초 실행 및 진행 기록 방식

다음 PowerShell 명령은 경로·기존 입력 확인용으로 현재 바로 사용할 수 있다. 학습 실행 명령은 아니다.

```powershell
Set-Location -LiteralPath 'D:\ssafy\ocr\mogumogu'
$ocrProject = (Get-Location).Path
$ocrWork = Join-Path $ocrProject 'full_receipt_20261117'
$ocrInputs = @(
  'dataset\receipt_labeled',
  'full_receipt_20261117\phone_baseline\audit_v2\manifest.jsonl',
  'full_receipt_20261117\round2\run_001\outputs_train\best_accuracy.pdparams',
  'full_receipt_20261117\round2\run_001\export\inference.pdiparams',
  'full_receipt_20261117\PaddleOCR'
)
$ocrInputs | ForEach-Object {
  [pscustomobject]@{Path=$_; Exists=(Test-Path -LiteralPath (Join-Path $ocrProject $_))}
}
Get-FileHash -Algorithm SHA256 -LiteralPath (Join-Path $ocrWork 'round2\run_001\export\inference.pdiparams')
Get-Command docker -ErrorAction SilentlyContinue
```

Docker CLI가 PATH에 없으면 기존 설치 위치 `%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin\docker.exe`를 확인한다. 실제 Docker 엔진·이미지·GPU 검사는 성공 여부를 기록한다. 과거 성공 기록만으로 현재 GPU 실행을 통과 처리하지 않는다.

실행 시 `R\progress\session_<시각>.json`을 새로 만들고 다음 필드를 기록한다. 이것은 기록 형식 예시이며 아직 생성된 실행 결과가 아니다.

```json

  "started_at": "실제 ISO8601 시각",

```

상태는 `pending / running / passed / failed / waiting_input / skipped_with_reason`으로 구분한다. 성공에는 run 경로와 검증 결과가 필요하다. 단계 종료·오류·중단 시 새 `session_<시각>_<순번>.json`을 저장한다. 재개할 때는 기록의 시각·경로·해시와 실제 프로세스 상태를 대조한다. JSON 상태만 믿고 실행 중 학습을 중복 시작하지 않는다.

## 4. 단계별 실행 체크리스트

### S00. 환경·입력·선행 결과 확인

- [ ] 프로젝트의 적용 AGENTS.md 및 상세 설계·이 진행 파일을 읽는다.
- [ ] 입력 데이터·manifest·모델·학습 checkpoint·기존 평가 파일 존재를 확인한다.
- [ ] 소스/설정/모델 해시, 저장소 commit, Docker 이미지 ID·패키지·GPU를 기록한다.
- [ ] 실행 중인 학습·평가가 있는지 확인하고 완료된 후속 run이 있으면 증거를 검증해 재사용한다.
- [ ] 2차 학습 가중치를 같은 설정으로 별도 export하여 기존 추론 모델과 동일성 검증 계획을 확정한다.

**통과:** 입력 누락·가중치 불일치를 식별했고, 실행 환경 검사가 성공했다. 미해결 항목은 해당 의존 단계만 대기시킨다. checkpoint가 존재한다는 이유만으로 선택 모델과 동일하다고 간주하지 않는다.

### S01. 실행기·평가기·상태 guard 구현

- [ ] `implementation_v1`에 새 실행기·평가기·영역 처리 wrapper·학습 데이터 준비 모듈을 구현한다. 기존 모듈을 재사용하되 하드코딩 경로·설정 누락을 제거한다.
- [ ] manifest/policy 해시, 새 run만 허용, 동일 run resume, freeze 후 변경 거부를 구현한다.
- [ ] 부분 GT CER·EM, 미매칭 삭제 기여, matched-only 분모, 미채점 예측 수를 분리한다.
- [ ] 빈 예측·다중 후보·동일 IoU·분할/병합·좌표 경계·변경된 입력의 재개 거부 테스트를 통과시킨다.
- [ ] `--help`와 실제 smoke를 확인한 **실행 가능한 명령만** `progress/commands_<시각>.ps1`에 저장한다.

**통과:** 새 코드 테스트·구문 검사 성공, 실제 소량 평가 완료, 명령과 출력 경로 기록. 구현 전 가상의 CLI 명령을 실행하지 않는다. 상세 설계의 모듈명은 구현 계약이지 존재 증명이 아니다.

### S02. 기존 기준 재현 및 데이터 분할 동결

- [ ] 기존 캐시로 전체 304장 기준 정수 집계·샘플 ID를 재현한다.
- [ ] 현재 환경에서 소량 추론 결과를 대조하고 차이가 없으면 기준 실행을 완료한다. 차이가 있으면 환경·전처리·유효 설정부터 확인한다.
- [ ] 원본 영수증·재촬영 그룹을 확인하고 이미지 hash·유사도·메타데이터 기반 중복 후보를 감사한다.
- [ ] 기존 304장을 그룹 기준 약 80/20, seed 42로 phone_train/phone_dev로 나눈다. 전체 split·제외 사유·실제 그룹 수를 기록한다.
- [ ] 학습 전 2차 모델의 phone_dev GT crop 및 부분 OCR 성능을 저장한다. 동일 phone_dev가 이후 비교의 기준이다.
- [ ] KORIE 공식 train/val/test는 변경하지 않고, 보류 사유와 전체 외부 val 평가 범위를 보존한다.

**통과:** train/dev 그룹 중복 없음, 평가 입력·분모·선택 규칙 고정. 304장은 이미 진단에 노출된 자료임을 표시한다. 미해결 중복 그룹은 학습 입력에 넣지 않는다. 전체 수동 라벨 검수는 시작 조건이 아니다.

### S03. 학습 전 영역 처리 개선

- [ ] 상세 설계 E01/E02에 따라 좌우 0/2/5%, 상하 0/2/5% 여백을 단계적으로 비교한다. 회전 방향·이미지 경계·인접 행을 처리한다.
- [ ] E03 분할은 실제 대응 근거가 있는 개발 사례에 한해 구현한다. GT 토큰 수만으로 행별 정답을 자동 배정하지 않는다.
- [ ] E04 병합은 동일 검출 캐시의 off/on 비교로 분리한다. 정확한 수량·숫자 열의 회귀를 기록한다.
- [ ] 정답→오답·오답→정답·매칭 변경·단계별 지연을 기록하고 phone_dev 기준으로 정책을 선택한다.
- [ ] 304장 전체 비교는 진단 표로 남기고, 선택에 사용한 표본 범위를 명시한다.

**통과:** 개선된 정책 또는 기존 정책 유지 결정과 근거가 저장됐다. 개선이 없더라도 S04로 진행한다. 분할/병합 근거가 부족하면 해당 옵션을 이유와 함께 보류하고 기본 off를 유지한다.

### S04. 스마트폰 학습 데이터와 초기 가중치 준비

- [ ] 검증 라벨과 대응 이미지에서 학습 crop·목록을 새 폴더에 생성한다. 좌표 이미지와 raw 이미지를 혼동하지 않는다.
- [ ] 이미지 로딩·라벨 파싱·NFC·사전 순서·OOV·길이·그룹 누수를 검사하고 보류 사유를 저장한다.
- [ ] 학습 불가 표본도 전체 외부 phone_dev 평가에 포함한다. 빈 라벨이나 손상 입력은 명시적 사유로 처리한다.
- [ ] 2차 `.pdparams`를 export하여 기존 기준과 가중치/예측 동일성을 검증한다. 누락·shape 불일치가 있으면 본 학습 금지다.
- [ ] train용 증강만 적용하고, dev·test에는 확률적 증강이나 BN 통계 갱신을 금지한다.

**통과:** train/dev 목록·분포·검사 결과·초기 모델 동일성 증거 확보. 부분 GT에서 검증된 crop으로 인식 학습은 가능하지만, 부분 GT 전체 이미지를 그대로 검출기 학습에 사용하지 않는다.

### S05. 실제 smoke와 학습 안정성 검사

- [ ] 별도 smoke run에서 train 최대 64개, 작은 batch, 2 epoch를 실행한다.
- [ ] loss·gradient·NaN/Inf·GPU 메모리·checkpoint 저장·export·실제 추론을 검사한다.
- [ ] 고정 입력 반복 평가 및 증강 없는 train 부분집합을 통해 설정·비결정성 문제를 먼저 조사한다.
- [ ] BN 가설 실험은 필요할 때만 모델 복제로 수행하고, train-only 통계 재보정 및 버퍼 해시를 기록한다.

**통과:** 실제 학습·export·평가가 완료됐다. smoke 가중치는 본 학습에 사용하지 않는다. GPU 메모리 부족은 batch를 줄인 새 시도로 해결하고 유효 batch와 설정 변경을 기록한다.

### S06. 최종 영수증 데이터셋 인식 튜닝

- [ ] 검증된 2차 학습 가중치에서 새 optimizer로 본 학습을 시작한다.
- [ ] 시작 설정은 seed 42, LR 1e-5, 최대 10 epoch, batch 16, 기존 구조·사전·증강 유지로 고정한다. 메모리에 따른 조정은 학습 시작 전에 기록한다.
- [ ] 매 epoch checkpoint를 보존하고 동일 전체 phone_dev GT crop 외부 CER로 선택한다. 동률이면 EM, 이후 이른 epoch 순이다.
- [ ] 최저 phone_dev CER 후보를 export하고 phone_dev 부분 OCR·숫자/기호·가능한 필드 지표 및 KORIE 전체 val을 평가한다.
- [ ] 선택 후보가 회귀 기준에 실패하면 기준 모델을 유지한다. test를 보지 않은 상태에서 후속 개발 실험 여부를 결정한다.

**통과:** 예정 학습 종료 또는 실패 원인·재개 상태 기록, 선택 checkpoint와 export, 전후 dev 평가 확보. 내부 학습 acc만으로 최종 모델을 정하지 않는다. 학습이 완료된 것과 기존 모델보다 개선된 것은 별도로 보고한다.

학습 후 전체 304장은 train 표본이 섞인 진단 결과다. 이 점수를 학습 전 304장 점수와 비교해 일반화 개선이라고 주장하지 않는다. 전후 효과 표는 phone_train, phone_dev, 전체 진단, 신규 test를 별도 행으로 구분한다.

### S07. 필요한 보완 실험만 수행

- [ ] KORIE 회귀 시 phone-only와 KORIE train 혼합을 독립 실험으로 비교한다. 혼합 비율·샘플링·epoch당 표본 수를 시작 전에 고정한다.
- [ ] 길이 문제가 확인되면 25/40, 폭 문제가 확인되면 320/480을 각각 독립 실험으로 수행한다. 실제 추론 resize와 CTC/NRTR 호환을 확인한다.
- [ ] OOV 확장은 충분한 train 예제·문자 인덱스·헤드 이식 검증이 있을 때만 진행한다.
- [ ] server·타일링·영상 보정 등은 측정 근거가 있을 때만 별도 실험으로 두고 모든 후보를 의무 실행하지 않는다.

**통과:** 선택한 보완 실험의 성공/실패와 미실행 이유를 남겼다. 결과를 보고 후보를 무한 확장하지 않는다. 최초 비교에서 채택 후보가 없으면 가장 큰 확인된 원인 한 가지에 대한 추가 실험 묶음만 수행한 뒤 모델 유지 여부를 결정한다.

### S08. 후보 조합·동결·최종 검증

- [ ] 선정된 인식기와 영역 정책을 조합해 동일 phone_dev에서 재검증한다. 개별 개선의 합이 실제 조합에서도 유지되는지 확인한다.
- [ ] 모델·정책·사전·split·평가 규칙·코드·컨테이너 해시를 동결한다.
- [ ] 신규 독립 test가 있으면 원본 영수증 그룹 중복 여부 확인 후 기준 모델과 후보를 동일 조건에서 평가한다.
- [ ] 독립 test가 없으면 `waiting_input`으로 남기고 학습/dev 완료 결과 및 배포 후보 패키지까지 정리한다. test 완료를 만들어내지 않는다.
- [ ] 완전 GT가 있으면 precision/recall·ignore 정책을 별도 평가하고, 없으면 부분 GT 지표만 보고한다.
- [ ] 동일 장비의 전체 OCR p95·메모리·실패율을 측정한다. 실제 API가 없으면 업로드·큐 포함 서비스 성능은 미확인으로 둔다.

**통과:** 동결 후보의 평가 및 최종 채택/기존 모델 유지 결정. 최종 test 결과로 다시 checkpoint를 고르지 않는다. test 도중 기술적 실패는 부분 결과로 선택하지 않고, 동일 동결 정책으로 미완료 입력만 재개하며 모든 시도를 남긴다.

### S09. 산출물 정리 및 종료 보고

- [ ] 학습 전후 표에 CER/EM·숫자/기호·금액/수량·미매칭·미채점·시간·메모리와 실제 평가 범위를 기록한다.
- [ ] 영수증 단위 paired 비교와 bootstrap 2,000회(seed 42)를 제공하고 개발 자료의 탐색적 구간임을 표시한다.
- [ ] 채택 모델 또는 유지 모델의 export 경로·가중치 해시·학습/평가 설정·재현 명령을 기록한다.
- [ ] 배포 후보 패키지와 사용 설명을 저장한다. 애플리케이션 자동 교체·운영 배포는 하지 않는다.
- [ ] 독립 test·필드 GT 등 미완료 항목과 다음에 필요한 입력을 정확히 남긴다.

**완료 구분:** `학습 완료`, `개발 평가 완료`, `독립 검증 완료`, `배포 후보 준비`를 각각 표시한다. 성능 개선이 없으면 기존 모델 유지도 유효한 결과지만, 수행하지 않은 검증을 완료로 처리하지 않는다.

## 5. 채택 규칙과 실패 시 재개

상세 설계의 보수적 개발 규칙을 적용한다. 동일 phone_dev에서 CER은 낮아지고 EM·숫자/기호 EM은 기준 이상이어야 한다. 필드 GT가 있으면 금액·수량 EM도 기준 이상이어야 한다. KORIE 전체 val CER은 기존 2차 기준보다 악화되지 않아야 하며, 로컬 전체 OCR p95는 재측정 기준의 1.10배 이내를 초기 비용 기준으로 둔다. 필드 GT 부족은 통과가 아니라 미확인이다. 이것은 후보 선별 규칙이며 제품 SLA나 성능 보장이 아니다.

| 상황 | 처리 및 다음 행동 |
|---|---|
| Docker/GPU 실패 | 로그·드라이버·엔진 상태 확인. 정상 설치 반복 금지. GPU 의존 작업만 대기하고 코드·데이터 검사는 계속 |
| 학습 checkpoint 불일치 | 본 학습 중단, 저장된 2차 checkpoint와 export 관계 조사. 추론 가중치 이름 변경 금지 |
| CUDA OOM | 실패 로그 보존. batch 조정은 새 run으로 시작; 기존 run resume에서는 설정 동일성을 유지 |
| 학습 중단 | 같은 run의 `.pdparams/.pdopt/.states` 완전성 확인 후 resume. 초기화된 optimizer를 resume으로 부르지 않음 |
| 평가 중단 | 입력·모델·정책 해시가 같을 때 미완료 항목만 새 attempt에 기록. 성공 결과 삭제·폴더 재사용 금지 |
| 라벨/그룹 정보 부족 | 해당 입력 보류·사유 기록, 충분한 검증 표본으로 가능한 개발 진행. 외부 dev 분모 변화는 새 버전으로 명시 |
| 완전 GT/신규 test 없음 | 검출 precision·독립 일반화 주장 보류. 인식 튜닝·dev·export는 계속 |
| 성능 악화 | 결과 보존, 원인 한 가지를 겨냥한 별도 개발 실험 또는 기준 유지. test로 재튜닝 금지 |

컨테이너 실행은 GPU와 충분한 shared memory를 사용하고 프로젝트는 읽기 전용, 새 작업 루트만 쓰기 가능하게 mount한다. 데이터 변환본·checkpoint·캐시는 새 작업 루트 안에 생성한다. 호스트 전체나 Docker socket을 컨테이너에 전달하지 않는다.
